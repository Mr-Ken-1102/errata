# 7. Nhưng điều đó có nghĩa ứng dụng của chúng ta bị lỗi không?

**Hiện chưa có bằng chứng để kết luận như vậy.**

Đây là điểm cần phân biệt rất cẩn thận.

Test hiện tại làm như sau về mặt dễ hiểu:

> Khởi động công việc → chờ tối đa 50 lần, mỗi lần yêu cầu đợi khoảng 1 ms → nếu công việc nền chưa tới điểm cần kiểm tra thì báo lỗi.

Đoạn thực tế:

```ts id="9s7n0x"
for (let attempt = 0; attempt < 50 && !lastAgentInput; attempt++) {
  await new Promise(resolve => setTimeout(resolve, 1))
}
```

Đây là cách test phụ thuộc vào **thời gian máy chạy**, thay vì đợi một tín hiệu chắc chắn rằng tác vụ đã tới đúng trạng thái.

Trên máy CI đang bận, `1 ms` không có nghĩa hệ điều hành sẽ thực sự cho code chạy lại đúng sau 1 ms.

## 17. Critical path

Hiện tại **không nên sửa Librarian runtime ngay** và cũng **không nên tiếp tục mở rộng Việt hóa trước**.

Thứ tự đúng là:

**Xác nhận flaky → làm test deterministic → sửa reporter CI → full validation → rồi mới tiếp tục Việt hóa.**

Điều kiện STOP rất rõ:

> Nếu một test deterministic vẫn chứng minh `povCharacterId` thật sự bị mất trong production path, dừng mọi công việc Việt hóa và chuyển sang sửa integration seam Didact × pax-co.

Ngược lại:

> Nếu test deterministic chạy ổn định và full suite sạch, không được sửa production Librarian chỉ vì một kết quả CI cũ.

Đây là ranh giới giúp tránh tình trạng “thấy đèn đỏ rồi sửa nhầm code đang đúng”.
